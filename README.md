# Todo App

Spring Boot todo manager with REST and MCP APIs.

## Run

Choose the profile at runtime. Both profiles connect to Oracle XE by default;
set the database password before starting:

```powershell
$env:DB_PASSWORD = "your_database_password"
$jwtBytes = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Fill($jwtBytes)
$env:JWT_SECRET = [Convert]::ToBase64String($jwtBytes)
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.profiles=dev"
```

If `JWT_SECRET` is unset, the app generates a temporary random signing key so
local development can start without extra setup. Tokens signed with this key
stop working after a restart, and separate app instances will not share tokens.
For persistent sessions or production, set a private `JWT_SECRET` in the same
PowerShell window before starting:

```powershell
$jwtBytes = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Fill($jwtBytes)
$env:JWT_SECRET = [Convert]::ToBase64String($jwtBytes)
```

`JWT_SECRET` must be base64 for at least 32 random bytes; keep it private and
use the same key across instances. Use HTTPS outside local development.

The app listens on port `8080` with the `/todo` context path. The todo UI is at
`http://localhost:8080/todo/`; the REST API is under
`http://localhost:8080/todo/api/todos`.

## Authentication

Create an account or sign in through the UI. Usernames are case-insensitive;
passwords must be at least 12 characters and no more than 72 UTF-8 bytes.
Passwords are stored as BCrypt hashes, never as plaintext. The registration
and login endpoints return a short-lived JWT (15 minutes by default):

```text
POST /todo/api/auth/register
POST /todo/api/auth/login
```

Send the returned token as `Authorization: Bearer <token>` when calling the
todo REST API or MCP endpoint. The browser UI keeps the token in session storage
and provides a sign-out action. Configure the signing lifetime with
`app.jwt.expiration` (for example, `PT30M`).

## Todo completion email

When a todo changes from active to complete, the app publishes a
`TodoCompletedEvent` to Kafka after the database transaction commits. A Kafka
consumer sends a notification to the configured mailbox; completing an already
completed todo does not send another notification.

Configure Kafka and SMTP before using notifications:

```powershell
$env:KAFKA_BOOTSTRAP_SERVERS = "localhost:9092"
$env:TODO_NOTIFICATION_EMAIL = "recipient@example.com"
$env:MAIL_FROM = "todos@example.com"
$env:SMTP_HOST = "smtp.example.com"
$env:SMTP_PORT = "587"
$env:SMTP_USERNAME = "your-smtp-username"
$env:SMTP_PASSWORD = "your-smtp-password"
```

The topic defaults to `todo-completed` and can be changed with
`TODO_COMPLETED_TOPIC`. Email credentials and addresses should be configured
through environment variables, not committed to source control.

## Profiles

The `dev` profile uses `spring.jpa.hibernate.ddl-auto=update`. The `qa` profile
uses `validate` so it checks the existing schema without modifying it. Both use
`localhost:1521/xe` and `c##app_user` by default. URL and username can be
overridden using environment variables:

```powershell
$env:DB_URL = "jdbc:oracle:thin:@localhost:1521/xe"
$env:DB_USERNAME = "your_database_username"
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.profiles=qa"
```

The QA profile validates against the existing schema and does not modify it.
Before using QA against a new database, create the users table:

```sql
CREATE TABLE users (
    id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR2(50 CHAR) NOT NULL UNIQUE,
    password_hash VARCHAR2(100 CHAR) NOT NULL,
    email VARCHAR2(254 CHAR),
    mobile_num VARCHAR2(20 CHAR),
    created_at TIMESTAMP NOT NULL,
    last_login_at TIMESTAMP
);
```

For an existing installation, rename `user_accounts` to `users`, add the new
fields, and backfill `created_at` before making it non-null:

```sql
ALTER TABLE user_accounts RENAME TO users;
ALTER TABLE users ADD (
    email VARCHAR2(254 CHAR),
    mobile_num VARCHAR2(20 CHAR),
    created_at TIMESTAMP,
    last_login_at TIMESTAMP
);
UPDATE users SET created_at = CURRENT_TIMESTAMP WHERE created_at IS NULL;
ALTER TABLE users MODIFY created_at NOT NULL;
```

Email and mobile number are optional at registration. `created_at` is set when
the account is created, and `last_login_at` is updated only after successful
password authentication. Every todo is associated with its creating user, and
REST and MCP operations only list or modify that user's todos.

For an existing `todos` table, add the ownership column and foreign key:

```sql
ALTER TABLE todos ADD user_id NUMBER;
ALTER TABLE todos ADD CONSTRAINT fk_todos_user
    FOREIGN KEY (user_id) REFERENCES users(id);
```

Existing todos remain unassigned and are not visible through the application;
assign them to the intended user with an `UPDATE` before deployment if they
should be retained.

Keep environment-specific credentials out of source control.
You can also select a profile when running the packaged application with
`java -jar target/todo-app-0.0.1-SNAPSHOT.jar --spring.profiles.active=dev`
(replace `dev` with `qa` as needed). No profile is selected automatically.

## MCP server

The Spring AI MCP server uses the Streamable HTTP transport. Connect an MCP
client to:

```text
http://localhost:8080/todo/mcp
```

It exposes `listTodos`, `getTodo`, `createTodo`, `updateTodo`,
`setTodoCompletion`, and `deleteTodo`. MCP tools and REST endpoints share the
same `TodoService` and database.
